# Spec Delta: Duel

## ADDED Requirements

### Requirement: DUEL-001 Real-Time Matchmaking and Rooms
The system MUST support real-time two-player duels using FastAPI WebSockets over same-origin endpoints under `/api/ws/duel/{room_id}`.
- **Matchmaking & Seats**: A duel room MUST only transition to the active playing state once two distinct player connections have successfully joined the room and been assigned to separate seats (Player 1/Seat 1 and Player 2/Seat 2).
- **Maximum Resources**:
  - Max rooms in worker memory: 100.
  - Max connections per room: exactly 2.
- **Third-Client Behavior**: Any connection attempt to a room that already has 2 registered players MUST be immediately rejected and closed with WebSocket close code `4001` ("Room Full").
- **Disconnect Handling**: If an active player disconnects, the server MUST mark the disconnected player as forfeited, declare the survivor the winner, cancel gravity loops, and mark the room status as `"finished"`.

#### Scenario: Duel starts only after two players join
- **GIVEN** an empty duel room with ID `room-123`
- **WHEN** Player 1 connects to `/api/ws/duel/room-123`
- **THEN** the room status remains "waiting" and no gameplay is started
- **AND WHEN** Player 2 connects to the same room
- **THEN** both players receive a "start" event and the room status transitions to "playing"

### Requirement: DUEL-002 Synchronized Piece Sequence and Mechanics
Both players in a duel MUST be fed the exact same sequence of starting and queued pieces generated by the server. Each player's board MUST advance independently, and use identical single-player score, level, lines, and collision mechanics.
- **Infinite Piece Queue**: To prevent exhaustion or reseeding divergence, the piece sequence MUST be lazily and deterministically generated using an index-based random generator initialized with a shared 32-bit room seed (`get_piece_at_index(index, seed)`). Each board MUST track its own `piece_index` (incremented on spawn). When a board spawns a piece at index `k`, it MUST retrieve the exact piece generated at index `k` for that seed.

#### Scenario: Verify identical starting piece sequence
- **GIVEN** a duel is starting
- **WHEN** the room transitions to "playing"
- **THEN** both Player 1 and Player 2 receive game states with identical active and next piece types

### Requirement: DUEL-003 Server-Driven Independent Gravity
Server-side gravity timers MUST drive game advancement independently for each board in a duel room, bypassing browser-side gravity timers. The server SHALL execute downward ticks on each player's board at its own dynamic gravity interval under a room-level lock, locking blocks and clearing lines automatically on the server, and broadcasting updated states to both clients.

#### Scenario: Server gravity ticks independently based on level
- **GIVEN** Player 1 is at level 1 (500ms gravity) and Player 2 is at level 2 (450ms gravity)
- **WHEN** time passes
- **THEN** the server triggers gravity ticks on Player 2's board more frequently than on Player 1's board

### Requirement: DUEL-004 WebSocket Messaging Envelope and Versioning
WebSocket messages between the client and server MUST be sent as structured JSON messages wrapped in a versioned envelope.
- **Envelope Fields**: `v: 1` (integer), `type` (string, enum), `timestamp` (ISO-8601 string), `seq` (integer, monotonic), `payload` (JSON object).
- **Extra-field policy**: Extra fields are strictly forbidden (Pydantic `extra="forbid"` is enforced).
- **UTF-8 frame size limit**: Max 4096 bytes (4 KB).
- **String field limits**: Max 64 characters, regex `^[a-zA-Z0-9_\-]+$` for IDs.

#### Client-to-Server (C2S) Schema:
1. **Type**: `"action"`
   - `action`: String enum (`"move_left" | "move_right" | "rotate_clockwise" | "rotate_counterclockwise" | "soft_drop" | "hard_drop" | "hold"`)
   - `seq`: Monotonic integer
   - `room_id`: String (max 64 chars)
   - `player_id`: String (max 64 chars)
   - `generation`: Integer (generation gate)
2. **Type**: `"heartbeat"`

#### Server-to-Client (S2C) Schema:
1. **Type**: `"start"`
   - `room_id`: String
   - `player1_id`: String
   - `player2_id`: String
2. **Type**: `"state"`
   - `room_id`: String
   - `seat`: Integer (1 or 2)
   - `player_id`: String
   - `board`: `List[List[Optional[str]]]` (20x10 grid)
   - `active_piece`: Optional `ActivePiece`
   - `status`: String (`"playing" | "game_over"`)
   - `score`: Integer
   - `total_lines`: Integer
   - `level`: Integer
   - `gravity_interval_ms`: Integer
   - `next_piece`: String
   - `hold_piece`: Optional[str]
   - `can_hold`: Boolean
   - `revision`: Integer (monotonic state revision)
   - `last_processed_seq`: Integer
3. **Type**: `"outcome"`
   - `room_id`: String
   - `winner_id`: Optional[str] (null on draw)
   - `loser_id`: Optional[str] (null on draw)
   - `is_draw`: Boolean
   - `reason`: String (`"top_out" | "forfeit"`)
4. **Type**: `"error"`
   - `message`: String

### Requirement: DUEL-005 Seat Authorization and Scoping
The server MUST strictly enforce seat ownership. A connected client MUST only be allowed to submit actions controlling their assigned seat (Player 1 or Player 2), verified via the client's authenticated connection state (bound during socket handshake). Any incoming message attempting to trigger movements on the opponent's board, or client-supplied scores, lines, or board matrix overrides, MUST be rejected immediately.

#### Scenario: Client attempts to control opponent board
- **GIVEN** Player 1 is assigned to Seat 1
- **WHEN** Player 1 sends a WebSocket message trying to move the piece on Seat 2's board
- **THEN** the server rejects the message, and Seat 2's board is unmodified

### Requirement: DUEL-006 Monotonic State, Duplicate Rejection and Generation Gate
The system MUST validate the monotonic sequence number and enforce a generation gate on all client WebSocket actions to prevent out-of-order and stale moves.
- **Monotonic Check**: The server MUST track `last_processed_seq` for each player and discard any incoming action where `seq <= last_processed_seq`.
- **Generation Gate**: Each board session MUST track a `generation` counter (starts at 0, incremented whenever a new piece is spawned or swapped from hold). Action messages MUST specify the expected `generation`. If the message `generation` does not match the server-side board's `generation`, the action MUST be rejected as stale, preventing keyboard inputs from leaking into the next spawned piece.

#### Scenario: Stale movement action is rejected
- **GIVEN** the server has already processed action sequence 10 and advanced the board to revision 11
- **WHEN** an action message arrives with sequence number 9
- **THEN** the server discards the message and does not mutate the game state

### Requirement: DUEL-007 Match Outcome, Draw Handling and Lock Grouping
To guarantee the concurrent same-update draw scenario, the server MUST serialize and group gravity tick evaluations under a room-level lock:
- **Grouped Update**: During a gravity update cycle, the server MUST evaluate gravity for both boards.
- **Same-Update Draw**: If both boards transition to `game_over` within the same update grouping (the same tick cycle), `evaluate_room_outcome()` MUST be executed once under the lock, recording `is_draw = True`, `winner_id = None`, and `loser_id = None`.
- **Outcome Single-Commit**: Outcomes MUST be committed exactly once. Once the room is set to `"finished"`, further ticks or movements MUST be strictly rejected.

#### Scenario: Declaring a winner
- **GIVEN** Player 1 tops out on their board
- **WHEN** Player 1's game-over status is processed and Player 2 is still playing
- **THEN** Player 2 is declared the winner, and both clients are notified of the outcome

#### Scenario: Match ended in a draw
- **GIVEN** both players have settled blocks near the top
- **WHEN** a concurrent server gravity tick causes both boards to top out simultaneously
- **THEN** both players are notified that the outcome is a "draw"

### Requirement: DUEL-008 Same-Origin Validation & CORS
The system MUST validate the handshake Origin header and maintain restrictive CORS.
- **Handshake Validation**: The WebSocket handshake MUST validate the `Origin` header against the authorized scheme, host, and port of the production proxy.
- **Rejection Policy**: If the `Origin` header is absent, null, or foreign (does not match), the server MUST immediately reject the connection (HTTP 403 Forbidden) and close the socket.
- **CORS Protection**: The REST endpoints MUST preserve the existing restrictive Stage 3 CORS policies and must not weaken them.
- **Proxy Configuration**: The frontend reverse proxy (Nginx) MUST correctly forward `Host`, `Origin`, and connection `Upgrade`/`Connection` headers to the FastAPI worker.

#### Scenario: Handshake is rejected for foreign origin
- **GIVEN** a WebSocket client attempts to connect with Origin "http://malicious-site.com"
- **WHEN** the server processes the handshake
- **THEN** the connection MUST be rejected with HTTP 403 Forbidden

### Requirement: DUEL-009 Bounded Room Retention Policy
The server MUST manage room lifecycles and release all memory allocated for inactive, abandoned, or completed duel rooms within 5 minutes of finalization or inactivity.
- **Inactivity Threshold**: exactly 240 seconds (4 minutes). Only explicit client gameplay actions (C2S messages of type `"action"`) reset the room's `last_input_time`. Heartbeat or automated gravity tick updates do NOT extend room lifetime.
- **Sweep Interval**: exactly 60 seconds.
- **GC Algorithm**:
  - A room in status `"finished"` MUST be released after 60 seconds.
  - A room in status `"waiting"` or `"playing"` MUST be released if `current_time - last_input_time > 240` (guaranteeing cleanup in max 300 seconds / 5 minutes, adhering strictly to the < 5 min bound).
- **Cleanup Testing**: Tests of this cleanup MUST use synthetic clock injection or mock timers, and controlled ticks, rather than real-time sleeping.

#### Scenario: Room cleanup of inactive rooms
- **GIVEN** a room in "playing" status with no action messages received for more than 240 seconds
- **WHEN** the 60-second sweeper runs
- **THEN** the room and its associated resources MUST be cleanly released from memory within 5 minutes of total inactivity

### Requirement: DUEL-010 Duel Separation and Solo Isolation
Duel outcomes, scores, and rooms MUST remain entirely isolated from the solo game SQLite database and leaderboard. Restarting a game in a duel room MUST initialize a fresh, synchronized room on the server and MUST NOT affect solo high scores.

#### Scenario: Duel outcomes do not modify solo database
- **GIVEN** a duel ends with Player 1 winning
- **WHEN** the results are finalized
- **THEN** no entry is added to the solo SQLite database table, and the solo leaderboard remains unchanged

### Requirement: DUEL-011 Dual-Board Side-by-Side Rendering
The frontend UI MUST render both authoritative boards side-by-side on separate Canvas elements (one local, one opponent), showing live occupied blocks, scores, levels, next piece, hold piece, and connection/player status indicators for both players.
- **Old-Socket & Stale UI Protection**:
  - On socket closure or reconnection, the client MUST clear all old callback handlers and replace them to avoid closures capturing stale state.
  - S2C state updates carrying a `revision` lower than the highest seen `revision` for that seat MUST be discarded.

#### Scenario: Opponent board updates in real time
- **GIVEN** the local player is rendered side-by-side with the opponent
- **WHEN** a state update for Seat 2 is received
- **THEN** the frontend MUST redraw the opponent's board on the separate Canvas element
